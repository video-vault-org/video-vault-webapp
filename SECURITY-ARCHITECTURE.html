01 · Was VideoVault schützt

VideoVault ist ein gemeinsames, Ende-zu-Ende-verschlüsseltes Videoarchiv. Dein Browser verschlüsselt Videos, Vorschaubilder, Titel, Beschreibungen und Kommentare, bevor sie den Server erreichen. Beim Ansehen entschlüsselt er sie auf deinem Gerät.

Der Server erhält beim normalen Anmelden weder dein Klartext-Passwort noch die offenen Archivschlüssel. Diese Eigenschaft wird hier als Zero-Knowledge bezeichnet. Sie ist kein mathematisches Zero-Knowledge-Beweisverfahren.

Bei der Ersteinrichtung verarbeitet ein lokales Einrichtungsprogramm das erste Admin-Passwort und speichert den Login-Prüfwert. Die Schlüsselfelder bleiben zunächst leer. Beim ersten erfolgreichen Anmelden erzeugt dein Browser die beiden unabhängigen 32-Byte-Archivschlüssel und einen zufälligen Passwortschlüssel-Salt. Er verpackt die Schlüssel mit dem lokal aus deinem Passwort abgeleiteten Passwortschlüssel. Nur der Salt und die verpackten Schlüssel werden gespeichert; die offenen Archivschlüssel verlassen den Browser nicht.

Die erste Schlüsselablage ist atomar und nur für das eigene Admin-Konto mit leerem userKey erlaubt. Bei gleichzeitigen Erst-Anmeldungen wird nur ein Schlüsselpaar gespeichert. Die Browser laden anschließend die gespeicherten Schlüssel und entsperren sie mit dem Passwort. Bis dies erfolgreich abgeschlossen ist, bleibt das Archiv in der Oberfläche gesperrt.

Ein gemeinsames Archiv hat gemeinsame Schlüssel. Über die Benutzerverwaltung hinzugefügte Konten erhalten dieselben Archivschlüssel, jeweils unter ihrem eigenen Passwort geschützt. Rollen regeln den Serverzugriff; sie erzeugen keine getrennten kryptografischen Bereiche.

02 · Welche Schlüssel welche Aufgabe haben

Schlüssel Aufgabe
Passwortschlüssel passwordKey Wird aus deinem Passwort abgeleitet und schützt die beiden Archivschlüssel deines Kontos.
Verschlüsselungsschlüssel masterEncryptionKey Schützt die individuellen Schlüssel für Dateien und verschlüsselte Texte.
Prüfschlüssel masterAuthKey Erzeugt und prüft die HMACs der Video- und Kommentar-Metadaten.
Dateischlüssel Ein frischer Zufallsschlüssel pro Video, Vorschaubild oder verschlüsseltem Text; verschlüsselt dessen Inhalt mit AES-256-GCM.

Die beiden Archivschlüssel werden unabhängig voneinander als jeweils 32 zufällige Bytes erzeugt. Ein Dateischlüssel ist ebenfalls 32 Bytes lang. Dein Passwort ist somit nicht unmittelbar der Schlüssel für die Videos.

03 · Passwort, Salt und Login-Nachweis

Aus demselben Passwort werden mit Argon2id zwei getrennte Werte abgeleitet. Unterschiedliche Salts trennen ihre Aufgaben:

  • Der loginHash dient als Login-Nachweis. Sein Salt ist die öffentliche Instanz-Salt, direkt gefolgt vom Benutzernamen, als UTF-8 kodiert.
  • Der passwordKey entsperrt die Archivschlüssel. Sein Salt ist ein eigener zufälliger 32-Byte-Wert (passwordKeySalt) pro Passwort-Einrichtung.

Argon2id verwendet 19 MiB Arbeitsspeicher, zwei Durchläufe, Parallelität 1 und 32 Bytes Ausgabe. Das Ausprobieren vieler Passwörter kostet damit Rechenzeit und Speicher. Ein starkes Passwort bleibt wichtig.

Die Instanz-Salt besteht aus 32 zufälligen Bytes in Hex-Darstellung und wird dem Browser öffentlich mitgeteilt. Sie ist kein geheimes Zusatzpasswort. Auch der persönliche Passwortschlüssel-Salt ist nicht geheim.

Zum Anmelden sendet der Browser den Base64-kodierten loginHash. Der Server speichert davon einen zusätzlich mit scrypt und einem eigenen zufälligen Salt geschützten Prüfwert. Der übertragene Login-Nachweis ist trotzdem wie ein Passwort zu behandeln: Wer ihn besitzt, kann sich damit anmelden, jedoch nichts entschlüsseln.

Passwortregeln und Prüfung auf Datenlecks

Oberfläche und Ersteinrichtung verlangen mindestens zwölf Zeichen und mindestens drei dieser vier Zeichenarten: Großbuchstaben, Kleinbuchstaben, Zahlen und Sonderzeichen.

Die Prüfung gegen Pwned Passwords überträgt nur die ersten fünf Hex-Zeichen eines SHA-1-Hashes und fordert Fülleinträge an. Der vollständige Vergleich findet lokal statt; SHA-1 dient ausschließlich dieser Suche. Der Dienst sieht die anfragende IP-Adresse und den Hash-Präfix. Ein Treffer wird abgelehnt. Ist die Prüfung nicht erreichbar, ist das Passwort mit einer Warnung zulässig.

Im normalen Webbetrieb sieht der Server das Passwort nicht und kann diese Eingaberegeln nicht selbst nachprüfen.

04 · Wie dein Konto die Archivschlüssel schützt

Die beiden Archivschlüssel werden einzeln mit deinem Passwortschlüssel durch AES-256-Key-Wrap geschützt. „Wrapping“ bedeutet hier, einen Schlüssel verschlüsselt zu verpacken. Erst das passende Passwort ermöglicht das Entpacken.

Aus jedem 32-Byte-Schlüssel werden 40 verpackte Bytes. Zuerst steht der verpackte Verschlüsselungsschlüssel, danach der verpackte Prüfschlüssel. Die zusammengefügten 80 Bytes werden als eine Base64-Zeichenfolge im userKey gespeichert.

Beim Entsperren dekodiert der Browser diese Zeichenfolge, trennt sie in zwei 40-Byte-Teile und entpackt beide mit dem lokal abgeleiteten Passwortschlüssel. Base64 selbst ist nur eine Kodierung, keine Verschlüsselung.

05 · Anmeldung und Berechtigungen

Nach erfolgreicher Anmeldung stellt der Server ein signiertes Zugriffstoken aus, ein JWT. Es ist standardmäßig eine Stunde gültig. Für die Signatur verwendet der Server HMAC-SHA-256 mit einem zufällig aus zehn eigenen 256-Bit-Schlüsseln gewählten Schlüssel. Diese Schlüssel sind von den Archivschlüsseln unabhängig.

Das Token erlaubt Zugriffe auf den Server, entschlüsselt aber keine Videos. Bei geschützten Anfragen prüft der Server das Token und lädt das Konto samt Rollen aus der Datenbank. Gelöschte Konten erhalten so keinen weiteren Serverzugriff. Der Browser speichert das Token in localStorage; wer es kopiert, kann es bis zu seinem Ablauf verwenden, solange das Konto besteht.

Berechtigung Möglichkeiten
Angemeldetes Konto Videos ansehen und herunterladen; Kommentare lesen, hinzufügen und eigene Kommentare bearbeiten oder löschen.
Admin Konten verwalten, Rollen vergeben und Zugangsdaten zurücksetzen.
Editor Videos hochladen, bearbeiten, Dateien ersetzen und Videos löschen.
Moderator Auch Kommentare anderer Personen bearbeiten oder löschen.

Die Rollen werden unabhängig vergeben. Ein Admin-Konto benötigt zum Verwalten von Videos zusätzlich die Editor-Rolle.

Schutz vor wiederholtem Raten

Nach dem fünften Fehlversuch für einen Benutzernamen gilt eine Sperre von 15 Sekunden. Weitere Fehlversuche nach Ablauf verdoppeln die Dauer auf 30 Sekunden, 60 Sekunden und so weiter, bis höchstens 15 Minuten. Ein Versuch während einer laufenden Sperre startet deren Dauer erneut, ohne den Zähler zu erhöhen. Eine erfolgreiche Anmeldung entfernt den Fehlversuchszähler.

06 · Einladungen und Änderungen am Konto

Ein weiteres Konto einladen

Ein angemeldeter Admin verwendet die bereits entsperrten Archivschlüssel, um sie unter einem zufällig erzeugten temporären Passwort für das neue Konto zu verpacken. Der Browser erzeugt dafür einen eigenen Passwortschlüssel-Salt und einen Login-Nachweis. Der Server erhält die verpackten Schlüssel, nicht deren Klartext.

Ein Einladungs- oder Reset-Link enthält Benutzernamen und temporäres Passwort im URL-Fragment hinter #, als Base64url-kodiertes JSON. Dieser Teil wird nicht mit dem HTTP-Aufruf an den Server gesendet. Die Anwendung entfernt ihn beim Einlesen aus der Adressleiste.

Der Zugangslink ist ein Geheimnis. Base64url verschlüsselt seinen Inhalt nicht. Wer den Link kennt, kennt das temporäre Passwort. Teile ihn nur über einen vertraulichen Kanal; auch Zwischenablage, Erweiterungen und gespeicherte Kopien können ihn offenlegen.

Beim Anmelden über den Link führt die Oberfläche zunächst zum Passwortwechsel. Diese Wechselpflicht liegt im Zustand der geöffneten Oberfläche und kann durch Neuladen umgangen werden. Der Server erzwingt keinen Wechsel, keine einmalige Link-Verwendung und keine eigene Link-Ablaufzeit. Das temporäre Passwort bleibt bis zum tatsächlichen Wechsel gültig.

Passwort oder Benutzernamen ändern

Beim Passwortwechsel werden dieselben Archivschlüssel mit einem neuen Passwortschlüssel und frischem Salt neu verpackt. Der Login-Nachweis wird ebenfalls erneuert. Die Videos müssen deshalb nicht neu verschlüsselt werden. Zum Ändern des eigenen Benutzernamens wird das aktuelle Passwort benötigt, weil der Benutzername Teil des Login-Salts ist.

Eine administrative Umbenennung erzeugt zugleich ein temporäres Passwort und einen Reset-Link. Umbenennung und Zurücksetzen erfolgen in getrennten Schritten; ein Fehler kann den Vorgang unvollständig lassen.

Ein Passwortwechsel beendet keine bereits ausgestellten Zugriffstokens und entzieht keine bereits bekannten Archivschlüssel. Wer sein Passwort vergessen hat, kann von einem anderen Admin mit entsperrten Archivschlüsseln einen neuen Zugang erhalten.

Ein Konto löschen

Der Server bearbeitet zuerst die zugehörigen Kommentare als Löschmarkierungen und entfernt danach das Konto. Das beendet dessen weitere Zugriffe auf den Server. Bereits kopierte Inhalte und Schlüssel werden dadurch nicht unbrauchbar.

07 · Wie Videos und Vorschaubilder verschlüsselt werden

Für jede Datei erzeugt der Browser einen frischen Dateischlüssel und verpackt ihn mit dem gemeinsamen Verschlüsselungsschlüssel. Der Dateiinhalt wird in Abschnitten von 34 KiB Klartext mit AES-256-GCM verschlüsselt. Der letzte Abschnitt kann kürzer sein.

Jeder Abschnitt erhält eine eigene zufällige 12-Byte-IV und einen 16-Byte-Authentisierungstag. Innerhalb einer Datei wird keine IV wiederverwendet. Der Tag erlaubt die Prüfung, ob Inhalt oder zugehörige Zusatzdaten verändert wurden.

Die authentisierten Zusatzdaten (AAD) binden jeden Abschnitt an Version 1, seinen Typ (Video oder Vorschaubild), den internen Dateinamen, seine Position ab 0 und die Gesamtzahl der Abschnitte. Die Dateinamen bestehen aus Video-ID und .video beziehungsweise .thumbnail. Die Zusatzdaten werden eindeutig als JSON nach RFC 8785 kodiert.

Vertauschte Abschnitte, ein anderer Dateikontext und abgeschnittene Inhalte scheitern an Format- oder Tag-Prüfungen. Auch eine leere Datei besitzt einen authentisierten leeren Abschnitt. Die Dateilänge erlaubt die Rekonstruktion der Abschnittsgrenzen.

Beim Abspielen und Herunterladen fordert der Browser nur die benötigten verschlüsselten Bereiche an. Er lädt betroffene Abschnitte vollständig, prüft und entschlüsselt sie und gibt erst dann die gewünschten Klartextbytes weiter. Ein geprüfter Abschnitt bedeutet nicht, dass schon die gesamte Datei geprüft wurde.

08 · Titel, Beschreibungen und Kommentare

Videotitel, Beschreibungen und Kommentar-Inhalte verwenden dasselbe Verschlüsselungsverfahren wie Dateien, jeweils mit einem eigenen frischen Schlüssel. Das verschlüsselte Ergebnis wird als Base64-Zeichenfolge gespeichert.

Die Zusatzdaten verwenden statt eines Dateinamens die Video- oder Kommentar-ID. Ein eigener Typ unterscheidet Titel, Beschreibung und Kommentar. So lässt sich ein gültiger Titel nicht einfach als Beschreibung oder Kommentar einsetzen.

Der Browser prüft aktive Datensätze und entschlüsselt die Texte für Anzeige und Suche im Arbeitsspeicher. Im Offline-Katalog bleiben Titel und Beschreibung verschlüsselt. Ein leerer Klartext wird als gültiger verschlüsselter Container mit einem leeren Abschnitt dargestellt.

Das Aufzeichnungsdatum recorded und die frei konfigurierbaren Metadatenfelder werden dagegen im Klartext gespeichert. Zusätzliche Metadatenfelder bieten keine Vertraulichkeit: Ein Name in einem solchen Feld ist für den Server lesbar.

09 · Integrität, sichtbare Daten und Löschmarkierungen

Ein HMAC-SHA-256 mit dem gemeinsamen Prüfschlüssel schützt die Video- und Kommentar-Metadaten. Er umfasst die fachlichen Attribute außer dem HMAC selbst. Datumswerte werden einheitlich als UTC-Zeit dargestellt; eine kanonische JSON-Darstellung nach RFC 8785 vermeidet Unterschiede bei der Serialisierung.

Bei verschlüsseltem Titel, Beschreibung und Kommentar geht nur die Länge der gespeicherten Base64-Zeichenfolge einschließlich Padding ein, nicht ihr Inhalt. Die AES-GCM-Tags prüfen den Inhalt. Das Metadaten-HMAC allein erkennt deshalb keinen Austausch gegen einen älteren gültigen Text derselben Identität und gespeicherten Länge.

Aktive Datensätze werden vor der Verwendung im Browser geprüft. Der Server speichert die HMACs, kann sie ohne den gemeinsamen Prüfschlüssel aber nicht selbst prüfen oder neu erzeugen.

Für den Server sichtbar Vor dem Server verschlüsselt
Benutzername, Anzeigename und Rollen; IDs und Zuordnungen Video- und Thumbnail-Inhalte
Aufzeichnungsdatum, Änderungszeiten und zusätzliche Metadaten Videotitel, Beschreibung und Kommentar-Inhalte
MIME-Typen, Datei- und Textlängen sowie Zugriffsmuster Die beiden Archivschlüssel im gespeicherten userKey

Was „Gelöscht“ bedeutet

Bei gelöschten Kommentaren leert der Server den Inhalt und setzt eine Löschmarkierung. Der Browser zeigt eine leere Hülle mit „Gelöscht“. Weil der Server keinen Prüfschlüssel besitzt, sind solche Markierungen nicht kryptografisch verifiziert; der Browser prüft deren HMAC nicht und versucht keine Textentschlüsselung.

Bei Videos werden Dateien und Kommentare entfernt, während ein dauerhafter Löschvermerk mit ID und Löschzeitpunkt für den Abgleich erhalten bleibt. Die Inhaltsfelder und der HMAC sind geleert. Der Browser entfernt das Video und sein zwischengespeichertes Thumbnail aus dem Offline-Katalog. Auch dieser Löschvermerk ist unverifiziert.

Ein Server kann Inhalte durch Löschmarkierungen oder Weglassen verbergen. Verschlüsselung garantiert keine Verfügbarkeit.

10 · Auf deinem Gerät: Schutz und Grenzen

Entsperren und Offline-Nutzung

Nach jedem Neuladen entsperrt dein Passwort die Archivschlüssel lokal. Passwort und offene Schlüssel werden von der Anwendung nicht dauerhaft gespeichert. Im Browserspeicher liegen das Zugriffstoken, die öffentliche Anwendungskonfiguration und das Kontoprofil mit verpackten Schlüsseln.

Im Offline-Katalog bleiben Titel und Beschreibung verschlüsselt; die übrigen Metadaten stehen im Klartext. Geladene Vorschaubilder werden verschlüsselt gespeichert. Die Daten sind nach Instanz-Salt und Konto getrennt. Offline-Entsperren benötigt ein gespeichertes Profil und ein lokal noch nicht abgelaufenes Token. Das ist keine erneute Berechtigungsprüfung durch den Server. Videos und Kommentare werden online geladen; Videos werden nicht dauerhaft offline gespeichert.

Abmelden entfernt das Token und beendet die geöffneten Medienfreigaben, lässt verschlüsselte Offline-Daten aber bestehen. „Offline-Daten löschen“ entfernt Katalog und Thumbnails dieses Kontos und meldet dich ab. Die öffentliche Konfiguration und das Kontoprofil mit verpackten Schlüsseln bleiben im Browserspeicher.

Ein Service Worker hält die lokalen App-Dateien offline verfügbar und vermittelt entschlüsselte Bereiche an den Player. Er bekommt keine dauerhafte Kopie der offenen Archivschlüssel. Die Seite muss für Wiedergabe und Download geöffnet und entsperrt bleiben.

Was die Verschlüsselung nicht abdeckt

Grenze Bedeutung für dich
Browser und ausgelieferte Anwendung Schadcode auf deinem Gerät, Browser-Erweiterungen oder ein manipulierter Anwendungscode können Passwörter, offene Schlüssel und Inhalte abgreifen. Ein Server, der bösartigen JavaScript-Code ausliefert, kann diesen Schutz umgehen.
Gemeinsame Archivschlüssel Andere Schlüsselinhaber können Inhalte kopieren und gültige HMACs erzeugen. Ein HMAC ist keine persönliche Signatur des angegebenen Autors. Kontolöschung und Rollenentzug machen bekannte Schlüssel und Kopien nicht unbrauchbar; eine automatische Schlüsselrotation findet nicht statt.
Passwortraten mit kopierten Daten Wer verpackte Schlüssel oder Prüfwerte kopiert, kann Passwortkandidaten offline testen. Argon2id und scrypt erhöhen die Kosten; die Anmeldesperre des Servers greift bei solchen Offline-Versuchen nicht.
Aktualität und Vollständigkeit Ein Server kann gültige ältere Dateien oder Datensätze erneut ausliefern oder Daten weglassen. Ein gültiger Tag oder HMAC beweist keine Aktualität.
Abgleich und Teiländerungen Der Katalog gleicht Änderungen anhand der von Clients gesetzten Änderungszeiten ab. Falsche Uhren oder rückdatierte Änderungen können den Abgleich stören. Datei- und Metadatenänderungen können teilweise gelingen. Verzögert sichtbare Kommentare können bei einer Sammellöschung fehlen.

Für den Betrieb über das Netzwerk benötigt die Anwendung HTTPS. Lokale HTTP-Aufrufe über localhost oder Loopback-Adressen werden vom Browser als sicherer Kontext zugelassen. Eine verschlüsselte Verbindung schützt den Transport, ersetzt aber kein vertrauenswürdiges Gerät und keinen vertrauenswürdigen Anwendungscode.

01 · What VideoVault protects

VideoVault is a shared, end-to-end encrypted video archive. Your browser encrypts videos, thumbnails, titles, descriptions and comments before they reach the server. It decrypts them on your device when you view them.

During normal sign-in, the server receives neither your plaintext password nor the unwrapped archive keys. This property is called zero knowledge here. It is not a mathematical zero-knowledge proof protocol.

During initial setup, a local setup program processes the first administrator’s password and stores the sign-in verifier. The key fields remain empty. On the first successful sign-in, your browser generates the two independent 32-byte archive keys and a random password-key salt. It wraps the keys using the password key derived locally from your password. Only the salt and wrapped keys are stored; the unwrapped archive keys never leave the browser.

The first key write is atomic and allowed only for an admin’s own account with an empty userKey. Concurrent first sign-ins store only one key pair. The browsers then load the stored keys and unlock them with the password. The interface keeps the archive locked until this succeeds.

A shared archive has shared keys. Accounts added through user management receive the same archive keys, each protected by its own password. Roles control server access; they do not create separate cryptographic compartments.

02 · The purpose of each key

Key Purpose
Password key passwordKey Derived from your password; protects the two archive keys stored for your account.
Encryption key masterEncryptionKey Protects the individual keys used for files and encrypted texts.
Authentication key masterAuthKey Creates and checks HMACs for video and comment metadata.
File key A fresh random key for each video, thumbnail or encrypted text; encrypts its contents with AES-256-GCM.

The two archive keys are generated independently, using 32 random bytes each. Each file key is also 32 bytes long. Your password therefore does not directly serve as the video encryption key.

03 · Passwords, salts and sign-in proof

Argon2id derives two separate values from the same password. Different salts separate their purposes:

  • loginHash is the sign-in proof. Its salt is the public instance salt directly followed by the username, encoded as UTF-8.
  • passwordKey unlocks the archive keys. Its salt is a separate random 32-byte value (passwordKeySalt) generated when password protection is set up.

Argon2id uses 19 MiB of memory, two passes, parallelism 1 and a 32-byte output. Testing many password guesses therefore costs processing time and memory. A strong password remains important.

The instance salt consists of 32 random bytes encoded as hexadecimal and is supplied publicly to the browser. It is not an additional secret password. The personal password-key salt is not secret either.

For sign-in, the browser sends the Base64-encoded loginHash. The server stores a verifier additionally protected with scrypt and a separate random salt. The transmitted sign-in proof must still be treated like a password: anyone who has it can use it to sign in, but cannot decrypt anything.

Password rules and breach checking

The interface and initial setup require at least twelve characters and at least three of these four categories: uppercase letters, lowercase letters, numbers and special characters.

The Pwned Passwords check transmits only the first five hexadecimal characters of a SHA-1 hash and requests padding entries. The full comparison happens locally; SHA-1 is used solely for this lookup. The service sees the requesting IP address and hash prefix. Matches are rejected. If the check is unavailable, the password is allowed with a warning.

During normal web use, the server does not see the password and cannot independently check these input rules.

04 · How your account protects the archive keys

The two archive keys are individually protected with your password key using AES-256 Key Wrap. Wrapping means encrypting a key for storage. The matching password makes unwrapping possible.

Each 32-byte key becomes 40 wrapped bytes. The wrapped encryption key comes first, followed by the wrapped authentication key. These 80 bytes are concatenated and stored as a single Base64 string in userKey.

To unlock them, the browser decodes that string, splits it into two 40-byte parts and unwraps both using the locally derived password key. Base64 itself is an encoding, not encryption.

05 · Sign-in and permissions

After successful sign-in, the server issues a signed access token, a JWT. Its default lifetime is one hour. The server signs it with HMAC-SHA-256 using a random choice from ten of its own 256-bit keys. These keys are independent of the archive keys.

The token allows access to the server but does not decrypt videos. For protected requests, the server checks the token and loads the account and its roles from the database. Deleted accounts therefore receive no further access to the server. The browser stores the token in localStorage; someone who copies it can use it until expiry while the account exists.

Permission Capabilities
Signed-in account View and download videos; read and add comments; edit or delete your own comments.
Admin Manage accounts, assign roles and reset credentials.
Editor Upload and edit videos, replace files and delete videos.
Moderator Edit or delete other people’s comments as well.

Roles are assigned independently. An admin account also needs the editor role to manage videos.

Protection against repeated guessing

The fifth failed attempt for a username starts a 15-second lock. Further failures after it expires double the duration to 30 seconds, 60 seconds and so on, up to 15 minutes. An attempt during a lock restarts its duration without increasing the counter. A successful sign-in removes the failed-attempt counter.

06 · Invitations and account changes

Invite another account

A signed-in admin uses the already unlocked archive keys to wrap them under a randomly generated temporary password for the new account. The browser generates a separate password-key salt and sign-in proof. The server receives the wrapped keys, not their plaintext.

An invitation or reset link contains the username and temporary password in the URL fragment after #, encoded as Base64url JSON. This part is not sent to the server in the HTTP request. The application removes it from the address bar when reading it.

The access link is a secret. Base64url does not encrypt its contents. Anyone who knows the link knows the temporary password. Share it only through a confidential channel; the clipboard, extensions and saved copies can also expose it.

Signing in through the link first leads to the password-change form. This requirement lives in the state of the open interface and can be bypassed by reloading. The server does not enforce a change, single-use links or a separate link expiry time. The temporary password remains valid until it is actually changed.

Change a password or username

A password change rewraps the same archive keys with a new password key and fresh salt. It also renews the sign-in proof. Videos therefore do not need re-encryption. Changing your own username requires your current password because the username is part of the sign-in salt.

Administrative renaming also generates a temporary password and reset link. Renaming and resetting happen in separate steps; an error can leave the operation incomplete.

A password change does not invalidate already issued access tokens or revoke already known archive keys. Someone who forgets a password can receive new access from another admin with unlocked archive keys.

Delete an account

The server first processes the account’s comments as deletion markers, then removes the account. This ends further access to the server for that account. Previously copied content and keys remain usable.

07 · How videos and thumbnails are encrypted

For each file, the browser generates a fresh file key and wraps it with the shared encryption key. File contents are encrypted with AES-256-GCM in chunks of 34 KiB of plaintext. The last chunk may be shorter.

Each chunk receives its own random 12-byte IV and a 16-byte authentication tag. IVs are not reused within a file. The tag allows changes to the content or associated data to be detected.

Additional authenticated data (AAD) binds every chunk to version 1, its context (video or thumbnail), the internal filename, its position starting at 0 and the total chunk count. Filenames consist of the video ID and .video or .thumbnail. Associated data is encoded using unambiguous JSON following RFC 8785.

Reordered chunks, a different file context and truncated content fail format or tag checks. Even an empty file has an authenticated empty chunk. File size allows chunk boundaries to be reconstructed.

For playback and downloads, the browser requests only the necessary encrypted ranges. It fetches affected chunks in full, verifies and decrypts them, then returns the requested plaintext bytes. A verified chunk does not mean the entire file has already been checked.

08 · Titles, descriptions and comments

Video titles, descriptions and comment contents use the same encryption procedure as files, each with a fresh individual key. The encrypted result is stored as a Base64 string.

Associated data uses the video or comment ID instead of a filename. A separate context distinguishes a title, description and comment. A valid title therefore cannot simply be substituted for a description or comment.

The browser verifies active records and decrypts texts in memory for display and searching. Titles and descriptions remain encrypted in the offline catalog. Empty plaintext is represented by a valid encrypted container with an empty chunk.

The recording date recorded and configurable metadata fields are stored in plaintext. Additional metadata fields provide no confidentiality: a name entered in such a field is readable by the server.

09 · Integrity, visible data and deletion markers

An HMAC-SHA-256 using the shared authentication key protects video and comment metadata. It covers the business attributes except the HMAC itself. Dates use a uniform UTC representation, and canonical JSON following RFC 8785 avoids serialization differences.

For encrypted titles, descriptions and comments, only the length of the stored Base64 string including padding is included, not its contents. AES-GCM tags check the contents. The metadata HMAC alone therefore cannot detect substitution of an older valid text with the same identity and stored length.

The browser verifies active records before use. The server stores HMACs but cannot check or recreate them without the shared authentication key.

What “Deleted” means

For deleted comments, the server clears the content and sets a deletion marker. The browser displays an empty shell labelled “Deleted”. Because the server does not have the authentication key, these markers are not cryptographically verified; the browser neither verifies their HMAC nor attempts text decryption.

For videos, files and comments are removed while a permanent deletion record retains the ID and deletion time for synchronization. Content fields and the HMAC are cleared. The browser removes the video and its cached thumbnail from the offline catalog. This deletion record is also unverified.

A server can hide content through deletion markers or omission. Encryption does not guarantee availability.

10 · On your device: protection and limits

Unlocking and offline use

After each reload, your password unlocks the archive keys locally. The application does not persist your password or unwrapped keys. Browser storage holds the access token, public application configuration and account profile with wrapped keys.

Titles and descriptions remain encrypted in the offline catalog; other metadata is plaintext. Loaded thumbnails are stored encrypted. Data is separated by instance salt and account. Offline unlocking needs a stored profile and a token that has not expired locally. It is not a fresh permission check by the server. Videos and comments are loaded online; videos are not persistently stored offline.

Signing out removes the token and ends active media capabilities but retains encrypted offline data. “Clear offline data” removes this account’s catalog and thumbnails and signs you out. Public configuration and the profile containing wrapped keys remain in browser storage.

A service worker makes local application assets available offline and passes decrypted ranges to the player. It does not receive a persistent copy of the unwrapped archive keys. The page must stay open and unlocked for playback and downloads.

What encryption does not cover

Limit What it means for you
Browser and delivered application Malware on your device, browser extensions or modified application code can capture passwords, unwrapped keys and content. A server delivering malicious JavaScript can bypass this protection.
Shared archive keys Other key holders can copy content and create valid HMACs. An HMAC is not the named author’s personal signature. Deleting an account or removing roles does not invalidate known keys and copies; keys are not automatically rotated.
Password guessing with copied data Someone who copies wrapped keys or password verifiers can test password guesses offline. Argon2id and scrypt increase the cost; server sign-in locks do not apply to these offline attempts.
Freshness and completeness A server can replay valid older files or records, or omit data. A valid tag or HMAC does not prove freshness.
Synchronization and partial changes The catalog synchronizes by client-supplied modification times. Incorrect clocks or backdated changes can disrupt synchronization. File and metadata changes may partially succeed. Delayed visibility can cause comments to be missed during bulk deletion.

Network deployments require HTTPS. Browsers allow local HTTP access through localhost or loopback addresses as secure contexts. An encrypted connection protects transport but does not replace a trusted device and trusted application code.

11 · Terms and algorithms at a glance

Term Meaning
Salt A non-secret input to password derivation. Different salts prevent the same password from producing the same derived value everywhere.
Wrapping Encrypting a key with another key; here AES-256-KW following RFC 3394.
GCM tag An encrypted chunk’s authentication tag. It belongs to AES-GCM and is separate from the metadata HMAC.
HMAC A keyed check for metadata; here HMAC-SHA-256 using the shared authentication key.
JWT A signed access token for the server; it contains no archive keys and does not decrypt content.
Base64 / Base64url A text representation of bytes. It does not provide confidentiality.
