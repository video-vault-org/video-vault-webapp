01 · Ziel und Vertrauensgrenzen

VideoVault schützt private Videos durch Ende-zu-Ende-Verschlüsselung. Video- und Thumbnail-Dateien, Videotitel, Beschreibungen und Kommentar-Inhalte werden vor der Übertragung im Client verschlüsselt. Die Master-Schlüssel liegen serverseitig ausschließlich gewrappt vor. Der Server übernimmt Anmeldung, Rollenprüfung und Speicherung.

„Zero-Knowledge“ bezeichnet hier das Ziel, dass der Server im regulären Webbetrieb weder das Klartext-Passwort noch entschlüsselte Inhalte oder ungeschützte Master-Schlüssel benötigt. Es handelt sich nicht um ein Zero-Knowledge-Beweisprotokoll.

Die lokale Admin-CLI ist die bewusste Bootstrap-Ausnahme: Sie verarbeitet das erste Passwort und erzeugt die ursprünglichen Schlüssel auf dem Rechner der ausführenden Person.

Backend und React-Frontend implementieren die hier beschriebenen Client-Verfahren. Die Umsetzung ist durch Tests geprüft, aber nicht unabhängig sicherheitsauditiert.

02 · Schlüssel und Aufgaben

Wert Erzeugung und Zweck Ablage
masterEncryptionKey 32 zufällige Bytes; wrappt individuelle Dateischlüssel. Klartext nur im vertrauenswürdigen Client; gewrappt im userKey.
masterAuthKey Unabhängige 32 zufällige Bytes; HMAC-SHA-256 für Metadaten. Klartext nur im Client; separat gewrappt im userKey.
passwordKey Argon2id aus Passwort und individuellem passwordKeySalt; 32 Bytes. Nur während der lokalen Schlüsselverarbeitung.
fileKey Neue 32 zufällige Bytes pro Verschlüsselung einer Datei oder eines Textes. Gewrappt am Anfang des verschlüsselten Objekts.
loginHash Base64-kodierte Argon2id-Ausgabe für die Anmeldung. Übertragung an das Backend; dort als zusätzlicher scrypt-Hash gespeichert.
JWT-Signaturschlüssel Separate serverseitige HMAC-Schlüssel; keine Inhalts- oder Metadatenschlüssel. ./jwtkeys

Alle berechtigten Nutzer teilen dieselben beiden Master-Schlüssel. Individuell sind das Passwort, der passwordKeySalt, der daraus abgeleitete passwordKey und die gewrappte Darstellung userKey. Alle Zufallswerte benötigen einen kryptografisch sicheren Zufallszahlengenerator.

Backend implementiert

03 · Erstinitialisierung und Passwortableitung

Die Startdateien für Server, Konfigurations-CLI und Admin-CLI stellen sicher, dass ./.salt existiert. Bei der ersten Erzeugung entstehen 32 zufällige Bytes, gespeichert als genau 64 Hex-Zeichen. Vorhandene Werte werden wiederverwendet; ungültige oder unlesbare Dateien führen zu einem Fehler. Neue Dateien erhalten Modus 0600 und werden atomar veröffentlicht.

Die Admin-CLI fragt Benutzername (mindestens 3 Zeichen), Anzeigename und maskiertes Passwort ab. Sie liest den Instanzwert aus ./.salt, vergibt eine UUID v4 und verweigert eine weitere Erstinitialisierung, sobald ein Admin vorhanden ist. 

A(P, S) = Argon2id(password=UTF8(P), salt=S,
                     version=0x13, memory=19456 KiB,
                     timeCost=2, parallelism=1, output=32 bytes)

loginHash       = Base64(A(password, UTF8(instanceSalt + username)))
passwordKeySalt = CSPRNG(32 bytes)
passwordKey     = A(password, passwordKeySalt)

0x13 bedeutet Argon2-Version 1.3 (dezimal 19). Die Speichergröße beträgt 19 MiB. Das Profil entspricht dem OWASP-Mindestprofil für Argon2id. Passwort und Salt-Strings werden als UTF-8 verarbeitet, ohne automatische Unicode-Normalisierung. Für den Login-Salt wird der gespeicherte Hex-Text verwendet, nicht dessen dekodierte 32-Byte-Darstellung.

Die CLI erzeugt die beiden ursprünglichen Master-Schlüssel unabhängig, wrappt sie und legt den ersten Nutzer nur mit der Admin-Rolle an. Temporäre Klartext-Schlüsselbuffer werden im finally-Block überschrieben; das ist keine Garantie, dass jede Kopie eines JavaScript-Strings aus dem Speicher verschwindet.

Anwendungskonfiguration und DynamoDB-Namensraum

npm run config:init fragt zuerst den Anwendungstitel, danach Datenbank und Storage ab. Der Titel wird über die saveConfig-Funktion in ./conf/app.json gespeichert, beispielsweise { "title": "Meine Videos" }. Vorhandene Titel dienen als Vorgabe; vor dem Überschreiben bestehender Konfigurationen wird eine Bestätigung verlangt. Erlaubt sind 1 bis 100 Zeichen nach dem Entfernen äußerer Leerzeichen. Ohne app.json gilt VideoVault; fehlerhafte oder unlesbare vorhandene Dateien führen zu einem Fehler.

Wenn in ./conf/db.json kein conf.tablePrefix gesetzt ist, leitet der DynamoDB-Adapter seinen Präfix bei der Initialisierung aus dem aktuellen Titel ab. CamelCase-Wortgrenzen und andere Trennzeichen werden zu Bindestrichen, diakritische Zeichen entfernt und ASCII-Buchstaben kleingeschrieben: VideoVault → video-vault-, Meine Videos → meine-videos-. Titel ohne ASCII-Buchstaben oder Ziffern erhalten app-<16 Hex-Zeichen aus SHA-256 des Titels>-. Ungewöhnlich lange normalisierte Titel werden auf 100 Zeichen gekürzt und erhalten ebenfalls einen Hash-Suffix. Der Tabellenname entsteht durch Anhängen von users, usernames, videos, comments oder login-attempts. Ein explizit gespeicherter conf.tablePrefix hat Vorrang. Die Config-CLI fragt den Präfix separat ab: Ein vorhandener Wert dient als Vorgabe, ansonsten wird die Vorgabe aus dem Titel abgeleitet. Der bestätigte Wert wird in der Datenbank-Konfiguration gespeichert und bleibt unabhängig von späteren Titeländerungen.

Konfigurationsänderungen erfordern einen Neustart. Ein geänderter Präfix wählt andere DynamoDB-Tabellen und kann diese bei der Initialisierung neu anlegen; bestehende Daten werden nicht automatisch verschoben. Ohne expliziten tablePrefix kann auch eine Titeländerung den Präfix ändern. Mit gesetztem tablePrefix bleibt der Tabellen-Namensraum bei Titeländerungen stabil. Unterschiedliche Titel mit derselben normalisierten Form können denselben Präfix ergeben. Der Anwendungstitel beeinflusst weder die Instanz-Salt noch die Passwortableitung oder die Master-Schlüssel.

Der Titel ist öffentliche Anzeigeinformation. Bootstrap gibt nur freigegebene Anwendungsfelder aus, keine Datenbank- oder Storage-Zugangsdaten. Der künftige Client soll den Titel als Text setzen, etwa über document.title, und nicht als HTML interpretieren. Das Objekt app kann später um Logo und Favicon erweitert werden; konfigurierbare Logo-/Favicon-Felder sind noch nicht implementiert; das Frontend verwendet mitgelieferte Assets.

Öffentlicher Bootstrap für den Client

Vor der Anmeldung ruft der Client GET /bootstrap über HTTPS unter derselben Origin auf. Die Route ist ohne Token erreichbar und liefert die Protokollversion, die öffentliche, stabile Instanz-Salt aus ./.salt, den Anwendungstitel unter app.title sowie die Frontend-Metadatenkonfiguration unter meta. Ein Beispiel mit einem fiktiven Salt-Wert: 

{ "version": 1, "instanceSalt": "abababababababababababababababababababababababababababababababab", "app": { "title": "VideoVault" }, "meta": { "recorded": { "withTime": false, "useAsFilter": true }, "fields": [], "sorting": [{ "source": "recorded", "direction": "desc" }, { "source": "title", "direction": "asc" }] } }

Das Response-Schema bindet die Version an 1 und die Instanz-Salt an genau 64 Hex-Zeichen. Der Client prüft die unterstützte Version und das Format, bevor er den loginHash ableitet. Er verwendet exakt den gelieferten Hex-Text, ohne Groß-/Kleinschreibung oder Kodierung zu ändern. Die Instanz-Salt ist öffentlich und kein Anmeldegeheimnis.

Der Server lädt die Instanz-Salt und die Anwendungskonfiguration einmal vor dem Start des HTTP-Servers. Requests auf /bootstrap verwenden den geladenen Wert, ohne Dateien zu lesen oder neue Salts zu erzeugen. Cache-Control: no-store verhindert persistentes HTTP-Caching; das Frontend speichert die Bootstrap-Antwort ausdrücklich in localStorage und lädt sie nur bei fehlendem Cache oder über „Anzeige-Konfiguration neu laden“ erneut. Die Route ist in Swagger als öffentlich dokumentiert.

Die Instanz-Salt wird bei Neustarts nicht rotiert und muss zusammen mit der Datenbank gesichert werden. Bestehende Installationen müssen die bisherige Salt-Datei unter dem neuen Namen ./.salt mit unverändertem Inhalt übernehmen. Eine Neuerzeugung verändert die Login-Ableitung vorhandener Nutzer.

Öffentliche Frontend-Metadatenkonfiguration

npm run meta:init speichert ./conf/meta.json. Bootstrap veröffentlicht diese Konfiguration unter meta: Darstellungs-/Filteroptionen für recorded, Feldschlüssel und Anzeigenamen, Typen und Mehrfachwert-Flags, Pflichtfeld-/Detailanzeige-/Filter-Flags sowie die geordnete Liste der Sortierfelder mit Richtung. Das sind öffentliche Felddefinitionen, keine Video-Metadatenwerte. Vertrauliche Informationen gehören nicht in Feldnamen oder Anzeigenamen.

Diese Einstellungen steuern ausschließlich das Frontend. Pflichtfeld- und Anzeige-Flags sind keine serverseitige Validierung oder Zugriffskontrolle; ausgeblendete Felder werden dadurch nicht aus API-Antworten entfernt. Video.meta bleibt ein beliebiges JSON-Objekt. Authentifizierung und Rollenprüfungen bleiben maßgeblich für API-Zugriffe. Das Frontend muss Namen als Text darstellen und Titel vor einer inhaltlichen Sortierung lokal entschlüsseln. Mehrfachwerte sind freie Arrays und werden lexikografisch elementweise in gespeicherter Reihenfolge verglichen. Fehlende Werte und leere Arrays stehen unabhängig von der Sortierrichtung zuletzt.

Die Metadatenkonfiguration wird beim Serverstart geladen und für Requests im Speicher gehalten. Ohne Datei gelten recorded ohne Uhrzeit, als Filter aktiviert, keine Meta-Felder sowie recorded absteigend und anschließend Titel aufsteigend. Bestehende Konfigurationen werden vor der Veröffentlichung auf eindeutige Schlüssel, gültige Feldtypen und konsistente Sortierreferenzen geprüft. Änderungen erfordern einen Neustart.

Backend implementiert

04 · userKey: Verpackung und Entpacken

wrappedMasterEncryptionKey = AES-256-KW(passwordKey, masterEncryptionKey)
wrappedMasterAuthKey       = AES-256-KW(passwordKey, masterAuthKey)
userKey = Base64(wrappedMasterEncryptionKey || wrappedMasterAuthKey)

Verwendet wird AES-Key-Wrap nach RFC 3394 ohne Padding mit dem definierten Initialwert A6A6A6A6A6A6A6A6. Ein 32-Byte-Schlüssel wird zu 40 Bytes. Beide Wrap-Vorgänge sind eigenständig; erst die Ergebnisse werden verbunden. 

bytes = Base64Decode(userKey)        // exakt 80 Bytes
wrappedEncryption = bytes.subarray(0, 40)
wrappedAuth       = bytes.subarray(40, 80)
masterEncryptionKey = AES-256-KW-Unwrap(passwordKey, wrappedEncryption)
masterAuthKey       = AES-256-KW-Unwrap(passwordKey, wrappedAuth)

Für das Aufteilen eignet sich Buffer.subarray() bzw. Uint8Array.subarray(); ein Node-Buffer besitzt keine splice()-Methode. Base64 wird mit dem Standardalphabet und Padding nach RFC 4648 verwendet. Vor der Verwendung sind die dekodierte Länge und beide Unwrap-Ergebnisse zu prüfen. Ein Fehler bricht das Entsperren ab.

Backend implementiert

05 · Anmeldung und Serverzugriff

  1. Der Client lädt die öffentliche Instanz-Salt über GET /bootstrap und prüft Protokollversion und Format.
  2. Der Client erzeugt den loginHash lokal nach der beschriebenen Argon2id-Ableitung und sendet Benutzername und diesen Base64-String über TLS.
  3. Das Backend behandelt den Base64-String als Passwort, ohne ihn vorher zu dekodieren. In der Datenbank liegt davon ein scrypt-String mit eigenem 16-Byte-Salt: N=2¹⁵, r=8, p=3, Ausgabe 32 Bytes. Der Vergleich erfolgt mit timingSafeEqual.
  4. Bei Erfolg wird ein HS256-JWT mit einem zufällig gewählten der zehn serverseitigen 32-Byte-Signaturschlüssel erstellt. Standardlaufzeit: eine Stunde. Prüfung umfasst Algorithmus, Signatur, Key-ID, Issuer, Audience und Ablaufzeit.
  5. Pro Anfrage wird der aktuelle Nutzer aus der Datenbank geladen. Rollen werden aus seinen aktuellen Flags gelesen, nicht aus dem Token übernommen. API-Antworten lassen loginHash aus.

Nach dem fünften Fehlversuch je Benutzername beginnt eine Sperre von 15 Sekunden. Weitere Fehlversuche nach Ablauf verdoppeln sie bis maximal 15 Minuten. Versuche während der Sperre starten deren Dauer neu, ohne den Zähler zu erhöhen. Erfolg entfernt den Zähler. Gleichzeitige Versuche desselben Namens werden innerhalb der einen AuthService-Instanz serialisiert.

Der übertragene loginHash ist ein wiederverwendbares Anmeldegeheimnis. Sein Besitz ermöglicht eine Anmeldung, auch ohne Kenntnis des ursprünglichen Passworts. Er darf ebenso wenig wie Tokens oder Passwörter geloggt werden. TLS bleibt erforderlich.

Admins verwalten Nutzer, Editors verwalten Videos, Moderators bearbeiten fremde Kommentare. Alle angemeldeten Nutzer dürfen Inhalte abrufen und eigene Kommentare verwalten. Diese API-Rechte sind von den gemeinsamen kryptografischen Schlüsseln getrennt.

Frontend implementiert

06 · Nutzer hinzufügen und Passwort ändern

Weiteren Nutzer anlegen

Der aktuelle, berechtigte Nutzer entsperrt seinen userKey lokal. Für den neuen Nutzer werden mit dessen Passwort ein neuer loginHash, ein frischer 32-Byte-passwordKeySalt und ein neuer passwordKey erzeugt. Die bereits vorhandenen Master-Schlüssel werden getrennt mit diesem neuen passwordKey gewrappt und als neuer userKey gespeichert. Es entsteht kein neues Master-Schlüsselpaar.

In diesem Verfahren verarbeitet der anlegende Client vorübergehend auch das anfängliche Passwort des neuen Nutzers. Das Frontend erzeugt einen Einladungslink mit temporärem Passwort im URL-Fragment; ein Protokoll mit öffentlichen Schlüsseln ist nicht Bestandteil dieser Architektur. Das Backend empfängt die fertigen Passwortattribute; es übernimmt nicht das Entschlüsseln oder Neu-Wrappen.

Passwort ändern

Der Client entschlüsselt die bestehenden Master-Schlüssel mit dem bisherigen passwordKey. Mit dem neuen Passwort und einem frischen passwordKeySalt leitet er einen neuen passwordKey ab und wrappt beide Master-Schlüssel neu. Gleichzeitig berechnet er den neuen loginHash. Das Backend hasht diesen mit scrypt und aktualisiert loginHash, passwordKeySalt und userKey zusammen.

Die Master-Schlüssel und vorhandenen Inhaltsverschlüsselungen bleiben dabei dieselben. Ein vergessenes Passwort kann ohne bereits entsperrte Schlüssel oder Hilfe eines anderen Schlüsselinhabers nicht zum Entschlüsseln des bisherigen userKey verwendet werden. Passwortänderungen widerrufen aktuell keine bereits ausgestellten JWTs.

Benutzernamen ändern

Der Benutzername ist Teil des Login-Salts. Der Client muss deshalb aus dem Passwort und instanceSalt + neuerBenutzername einen neuen Base64-loginHash ableiten. Ein Umbenennen allein im Backend kann diesen Wert nicht aus dem bisherigen Hash rekonstruieren.

Beide Backend-Routen verlangen nun einen JSON-Body mit { "loginHash": "…" }: PATCH /api/user/change/username/:username für den eigenen Nutzer und PATCH /api/user/change/username/:userId/:username für Admins. Der Service hasht den neuen loginHash mit scrypt und einem frischen Salt. Alle fünf DB-Adapter speichern Benutzername und scrypt-Hash gemeinsam atomar; bei einem Namenskonflikt bleibt beides unverändert. Auch bei unverändertem Benutzernamen wird der mitgegebene Hash aktualisiert.

passwordKeySalt, userKey und die Master-Schlüssel müssen nicht geändert werden, da die passwordKey-Ableitung nicht vom Benutzernamen abhängt. Auch ein Admin benötigt den passend neu abgeleiteten loginHash; das Backend erhält dafür kein Klartext-Passwort. Das Frontend implementiert die Ableitung. Bei administrativer Umbenennung wird zugleich ein temporäres Passwort erzeugt und der userKey neu gewrappt; die zwei Backend-Aufrufe sind keine gemeinsame Transaktion.

Frontend implementiert

07 · Dateien: Verschlüsselung und Binärformat

Für jede neue Verschlüsselung einer Video- oder Thumbnail-Datei erzeugt der Client einen frischen, zufälligen 32-Byte-fileKey. Er wrappt ihn mit dem masterEncryptionKey mittels AES-256-KW. Auch bei einem Dateiaustausch wird ein neuer fileKey erzeugt.

Der Klartext wird in Chunks von höchstens 34 KiB = 34.816 Bytes geteilt. Jeder Chunk wird mit AES-256-GCM und demselben fileKey, aber eigener 12-Byte-IV verschlüsselt. Pro fileKey darf eine IV niemals wiederverwendet werden. IVs werden kryptografisch zufällig erzeugt; eine Wiederholung innerhalb derselben Datei muss ausgeschlossen werden. Jeder Chunk besitzt einen 16-Byte-GCM-Tag. 

wrappedFileKey = AES-256-KW(masterEncryptionKey, fileKey)
chunk[i]       = IV[i] || encryptedChunkContent[i] || GCMtag[i]
encryptedFile  = wrappedFileKey || chunk[0] || … || chunk[N−1]

Additional Authenticated Data (AAD)

Die AAD ist UTF-8-kodiertes kanonisches JSON nach RFC 8785 mit genau diesen Feldern:

Feld Bedeutung
version Die Zahl 1 für dieses Protokollprofil.
context video, thumbnail, title, description oder comment.
identity Bei Dateien der exakte Storage-Name <videoId>.video bzw. <videoId>.thumbnail; bei Texten die Video- bzw. Kommentar-ID.
chunkIndex Ganzzahl ab 0 für die Position dieses Chunks.
chunkCount Gesamtzahl der Chunks; mindestens 1. 
{"chunkCount":2,"chunkIndex":0,"context":"video","identity":"<videoId>.video","version":1}

Die Klartext-Gesamtlänge ist ausdrücklich kein AAD-Feld. Identitäten werden unverändert verwendet, ohne Unicode-Normalisierung oder Umdeutung in lokale Pfade. AAD wird authentisiert, aber nicht verschlüsselt und nicht zusätzlich im Binärformat abgelegt. Der Client rekonstruiert sie aus dem bekannten Objektkontext und der Chunk-Struktur. Für Version 1 gelten die hier festgelegten Größen; eine zukünftige Version benötigt eine explizite Protokollvereinbarung.

Grenzen, Vollständigkeit und Range-Zugriff

Alle Chunks außer dem letzten enthalten exakt 34.816 Klartext-Bytes. Der letzte enthält 1 bis 34.816 Bytes; nur eine leere Datei erhält genau einen leeren, authentisierten Chunk. Damit hat eine leere verschlüsselte Datei 68 Bytes. Ein voller Chunk belegt 34.844 Bytes. 

C = 34816                      // maximale Klartext-Bytes pro Chunk
B = C + 12 + 16 = 34844         // volle verschlüsselte Chunk-Größe
L = Klartextlänge in Bytes
N = max(1, ceil(L / C))
F = 40 + L + 28 × N             // gesamte verschlüsselte Dateigröße
offset(i) = 40 + i × B

Bei einer vollständigen Datei lässt sich die Zahl der Chunks als N = ceil((F − 40) / B) bestimmen. Der Parser prüft mindestens 68 Gesamtbytes, gültige Chunk-Grenzen und die zulässigen Größen einschließlich des leeren Sonderfalls. Er darf eine Teilantwort nicht als vollständige Datei interpretieren; bei Range-Zugriffen wird zusätzlich die Gesamtgröße des verschlüsselten Objekts benötigt.

Der Client verifiziert den GCM-Tag jedes Chunks gegen die erwartete AAD, bevor er dessen Klartext ausgibt. Vertauschte Chunks verletzen den Index, vollständiges Abschneiden oder Anhängen verändert die gebundene Chunk-Anzahl, und Änderungen innerhalb eines Chunks scheitern an dessen Tag. Ein bereits verifizierter Chunk beweist noch nicht, dass der restliche Download vollständig eingetroffen ist.

Ein GCM-Tag ist keine separate HMAC-SHA-256-Ausgabe. Er gehört zur authentisierten AES-GCM-Verschlüsselung und schützt Ciphertext sowie AAD. Das spätere Metadaten-HMAC hat eine eigene Aufgabe und einen eigenen Schlüssel.
Frontend implementiert

08 · Videotitel, Beschreibungen und Kommentar-Inhalte

Videotitel, Beschreibungen und Kommentar-Inhalte verwenden dasselbe Verfahren wie Dateien: UTF-8-Klartext, ein neuer zufälliger 32-Byte-fileKey, AES-KW mit masterEncryptionKey, 34-KiB-Chunks und AES-256-GCM. Der vollständige binäre Container wird anschließend Base64-kodiert und im Textfeld der Datenbank gespeichert. 

title       = Base64(wrappedFileKey || chunks)  // context="title", identity=videoId
description = Base64(wrappedFileKey || chunks)  // context="description", identity=videoId
content     = Base64(wrappedFileKey || chunks)  // context="comment", identity=commentId

Die AAD enthält zusätzlich wie bei Dateien Version, Chunk-Index und Chunk-Anzahl. Für die Beschreibung ist die Identität ebenfalls die Video-ID; der eigene Kontext description verhindert ein Vertauschen mit dem Titel desselben Videos. Jeder Textwert erhält einen eigenen frischen fileKey. Der getrennte Kontext verhindert einen Austausch zwischen einem Titel und einem Kommentar mit derselben ID. Jede neue Verschlüsselung, auch beim Bearbeiten eines Textes, erhält einen neuen fileKey. Vor der Anzeige werden Base64 dekodiert, der fileKey entwrappt und alle GCM-Tags geprüft.

Ein regulär verschlüsselter leerer Text ist ein Base64-Container mit einem authentisierten leeren Chunk. Er ist von content='' eines serverseitigen Tombstones zu unterscheiden. Base64 ist nur die Transport- und Speicherkodierung; die Vertraulichkeit stammt aus AES-GCM.

Backend-Vertrag für Beschreibung und Aufzeichnungsdatum

Neue Videos enthalten verpflichtend description als verschlüsselten Base64-String und recorded als Aufzeichnungsdatum. Der Server behandelt die Beschreibung als undurchsichtigen Text mit 1 bis 1.000.000 Zeichen; die clientseitige Verschlüsselung entspricht dem Titel-Verfahren. Ein leerer Klartext wird als gültiger verschlüsselter Container übertragen, nicht als leerer String. Das Aufzeichnungsdatum ist sichtbar, wird im Domänenmodell als Date verarbeitet und in HTTP-JSON als UTC-ISO-Zeitstempel ausgegeben. Sein vollständiger Wert geht nach der Datumsnormalisierung in das Metadaten-HMAC ein, während die Beschreibung dort nur mit ihrer gespeicherten Länge eingeht.

Die Editor-Routen PATCH /api/video/change/description/:videoId und PATCH /api/video/change/recorded/:videoId verlangen das jeweilige neue Feld sowie lastModified und hmac. Der VideoService und alle fünf Datenbankadapter unterstützen diese Aktualisierungen; das jeweilige Feld, lastModified und HMAC werden gemeinsam atomar gespeichert. Andere Felder bleiben erhalten. Das Backend erzeugt oder prüft die Beschreibungskryptografie und das Metadaten-HMAC nicht selbst.

Frontend implementiert

09 · Metadaten-Integrität und Tombstones

Der Client erzeugt das Metadaten-HMAC mit masterAuthKey und HMAC-SHA-256. Die Eingabe ist eine kanonische Darstellung aller fachlichen Attribute des jeweiligen Video- oder Kommentar-Datensatzes, mit diesen Regeln:

  1. Das Feld hmac und interne Datenbank-Hilfsfelder werden ausgeschlossen.
  2. Verschlüsselte Textwerte werden durch ihre Länge in der gespeicherten Form ersetzt: title, description bzw. content enthält in der HMAC-Projektion eine Zahl statt des Base64-Strings. Bei kanonischem Base64 entspricht die Zeichenzahl der UTF-8-Bytezahl; mitgezählt wird das Padding. Es ist weder die Klartextlänge noch die Länge des dekodierten Containers.
  3. Alle übrigen Attribute bleiben inhaltlich erhalten. Das umfasst IDs, MIME-Typen, JSON-meta, das unverschlüsselte Aufzeichnungsdatum recorded, Zeitstempel sowie bei Kommentaren Autor, Video-Zuordnung und Flags.
  4. Datumswerte werden vor der Kanonisierung als UTC-ISO-Strings entsprechend toISOString() dargestellt. Die Projektion enthält nur gültige JSON-Werte, keine undefined-Werte oder nicht-endlichen Zahlen.
  5. Serialisierung erfolgt per RFC 8785 (JCS), danach UTF-8-Kodierung und HMAC-SHA-256. Die 32-Byte-Ausgabe wird als Standard-Base64 gespeichert.
projection(video)   = allBusinessAttributesExceptHmac(video)
projection.title       = storedVideo.title.length
projection.description = storedVideo.description.length

projection(comment) = allBusinessAttributesExceptHmac(comment)
projection.content  = storedComment.content.length

hmac = Base64(HMAC-SHA-256(masterAuthKey, UTF8(JCS(projection))))

Die Feldnamen bleiben erhalten: Die Projektion ersetzt beispielsweise "title":"…" durch "title":92, ohne ein zusätzliches titleLength-Feld einzuführen. Änderungen erfordern ein neues HMAC über den vollständigen resultierenden Datensatz. Der Client verifiziert es vor der Verwendung; das Backend speichert es, kann es ohne masterAuthKey aber weder prüfen noch selbst erzeugen.

Das Metadaten-HMAC bindet bewusst nur die gespeicherte Länge eines verschlüsselten Textes. Es authentisiert nicht dessen konkreten Base64-Inhalt. Dafür sind die GCM-Tags zuständig. Ein früherer gültiger Ciphertext desselben Kontexts und derselben ID mit gleicher gespeicherter Länge kann damit nicht allein über das Metadaten-HMAC als veraltet erkannt werden.

Ausnahme: serverseitige Löschmarkierungen

Beim Soft-Delete setzt das Backend deleted=true und content=''. Das gilt für eigene Kommentare, Moderation und die Kommentare eines gelöschten Nutzers. Da der Server keinen masterAuthKey besitzt, kann er kein neues gültiges HMAC für den geänderten Datensatz erzeugen; der bisherige HMAC-Wert darf nicht als gültiger Nachweis interpretiert werden.

Tombstones sind ausdrücklich nicht kryptografisch verifiziert. Der Client zeigt sie als serverseitige Löschmarkierung und nicht als authentisierten Kommentar an. Er versucht nicht, den leeren Inhalt zu entschlüsseln. Auch die verbleibenden Tombstone-Metadaten sind damit nicht kryptografisch bestätigt. Ein manipulierter Server kann folglich Inhalte als gelöscht verbergen; die Architektur verhindert keine Löschung oder Unterdrückung von Daten.

10 · Schutzwirkung und Grenzen

Implementierter Browser- und Offline-Betrieb

Das eigenständige React-Projekt unter frontend/ arbeitet als PWA über HTTPS (für Entwicklung auch localhost). Der Service Worker hält ausschließlich die lokalen App-Assets im Cache. JWT, Bootstrap-Antwort und das Benutzerprofil mit gewrapptem userKey liegen in localStorage. Das JWT ist ein Bearer-Geheimnis: Schadcode desselben Ursprungs kann es lesen; XSS oder ein manipuliertes Frontend können auch entsperrte Schlüssel und Klartexte abgreifen.

Nach jedem Neuladen ist das Passwort zum lokalen Entsperren erforderlich. Entschlüsselte Master-Schlüssel bleiben nur im Arbeitsspeicher der geöffneten Seite. Bei 401 oder Abmeldung werden Token und laufende Medienfreigaben entfernt. Ein Offline-Entsperren verwendet das zuvor geladene Profil und ein noch nicht abgelaufenes Token; es ist keine aktuelle serverseitige Berechtigungsprüfung. Die UI-Rollen ersetzen niemals die Backend-Prüfung.

IndexedDB speichert den Katalog einschließlich verschlüsseltem Titel und verschlüsselter Beschreibung, die letzte synchronisierte Änderungszeit und bereits geladene verschlüsselte Thumbnails, getrennt nach Instanz-Salt und Benutzer-ID. Entschlüsselte Texte oder Vorschaubilder werden dort nicht gespeichert. Die fachlichen Metadaten einschließlich recorded bleiben wie auf dem Server unverschlüsselt. „Offline-Daten löschen“ entfernt den Cache dieses Kontos; normales Abmelden lässt den verschlüsselten Cache bestehen.

Die Synchronisation lädt zunächst /api/video/0, später Änderungen ab der höchsten bekannten lastModified. /api/video/catalog liefert angemeldeten Nutzern die aktuellen IDs für den Löschabgleich. Ciphertext und Cursor werden gemeinsam erst nach erfolgreicher Integritätsprüfung gespeichert. Der Abgleich ist kein kryptografischer Nachweis gegen Unterdrückung von Daten, kein transaktionaler Snapshot und kein Schutz gegen falsche Client-Uhren oder rückdatierte Änderungen.

Range-Wiedergabe und Download

Das Backend stellt authentisierte HEAD- und HTTP-Range-Abfragen der verschlüsselten Videodatei bereit. Ein temporärer, zufälliger Medienpfad im Service Worker übersetzt Player-Anfragen in Nachrichten an die entsperrte Seite. Dort werden die vollständigen betroffenen Chunks geladen, ihre Tags und AAD geprüft und nur die angefragten Klartextbytes zurückgegeben. Der Service Worker streamt diese Bytes in begrenzten Blöcken an Player oder Download; Klartext-Videos werden nicht persistent gecacht. Die Seite muss dabei offen und entsperrt bleiben. Videos sind zunächst nicht offline verfügbar.

Passwortregeln und Einladungen

Das Frontend verlangt mindestens 12 Zeichen und drei von vier Kategorien (Groß-/Kleinbuchstaben, Zahlen, Sonderzeichen). Diese UI-Regel ersetzt keine zusätzliche serverseitige Richtlinie. Beim Absenden prüft der Browser Pwned Passwords über die Range-API: Nur fünf Hex-Zeichen des SHA-1-Hashes werden mit Add-Padding: true übertragen; der vollständige Vergleich bleibt lokal. SHA-1 dient ausschließlich der Suche, nicht der Passwortableitung. Der Dienst sieht IP-Adresse und Präfix. Treffer werden abgelehnt; bei Ausfall wird mit Warnung fortgefahren.

Beim Anlegen oder administrativen Passwort-Reset erzeugt der Browser ein zufälliges temporäres Passwort und wrappt die gemeinsamen Master-Schlüssel neu. Ein einmalig angezeigter Link enthält {type: invite|reset, username, password} als Base64url-JSON im Fragment. Fragmente werden nicht als Teil des HTTP-Requests gesendet, bleiben aber Geheimnisse: Verlauf, Zwischenablage, Erweiterungen und Empfänger können sie lesen. Die App entfernt das Fragment sofort beim Einlesen und verlangt danach einen Passwortwechsel. Diese Verpflichtung wird ausdrücklich nur im Frontend durchgesetzt, Links sind serverseitig weder einmalig noch mit eigener Ablaufzeit versehen. Bestehende JWTs werden durch einen Passwortwechsel nicht widerrufen.

Die Architektur schützt die Vertraulichkeit von Inhalten gegenüber einem Server oder Storage, der nur verschlüsselte Daten verarbeitet. Authentisierte Verschlüsselung erkennt Manipulationen im gebundenen Kontext; der gemeinsame HMAC schützt die Integrität von Metadaten gegenüber Parteien ohne masterAuthKey.

Grenze Bedeutung
Sichtbare Metadaten Benutzernamen, Anzeigenamen, Rollen, IDs, Beziehungen, Zeitstempel einschließlich recorded, MIME-Typen, Dateigrößen und Zugriffsmuster bleiben für das Backend sichtbar. meta ist nicht automatisch verschlüsselt; dort abgelegte Klartextwerte bleiben lesbar.
Gemeinsame Schlüssel Kontolöschung sperrt weitere API-Zugriffe, entzieht aber keine bereits kopierten Schlüssel oder Daten. Echter kryptografischer Entzug erfordert Schlüsselrotation und gegebenenfalls Neuverschlüsselung; er macht frühere Kopien nicht unlesbar.
Keine individuelle Signatur Jeder Inhaber des masterAuthKey kann gültige HMACs erzeugen. Ein gültiger HMAC beweist daher nicht, welcher konkrete Nutzer einen Datensatz erstellt hat; Rollen und Autorenzuordnung werden vom Backend durchgesetzt.
Keine automatische Aktualität Ein früherer gültiger Datensatz oder eine frühere gültige Datei kann erneut ausgespielt werden. Zeitstempel im HMAC binden ihren Wert, beweisen ohne vertrauenswürdigen Vergleichszustand aber keine Aktualität.
Client-Vertrauen XSS, kompromittierte Browser-Erweiterungen oder manipuliertes ausgeliefertes JavaScript können Passwort und Schlüssel abgreifen. Die Vertraulichkeitszusage setzt vertrauenswürdigen Client-Code und ein vertrauenswürdiges Endgerät voraus.
Passwortangriffe Ein gestohlener userKey und passwordKeySalt erlauben Offline-Passwortversuche über die Unwrap-Prüfung. Argon2id verteuert diese Versuche; starke Passwörter bleiben erforderlich.
Wiederherstellung Ohne einen verfügbaren berechtigten Schlüsselinhaber gibt es keine serverseitige Wiederherstellung der Master-Schlüssel. Backups müssen Datenbank, Storage, stabilen Instanz-Salt und benötigte Konfiguration konsistent sichern.

Die Bezeichnung „Zero-Knowledge“ ist somit eine begrenzte Architekturaussage und keine Zusage, dass ein aktiver Serverangreifer, ein berechtigter Schlüsselinhaber oder ein kompromittierter Client keinerlei Schaden verursachen kann.

01 · Goals and trust boundaries

VideoVault protects private videos with end-to-end encryption. Video and thumbnail files, video titles, descriptions and comment contents are encrypted in the client before transmission. The server holds master keys only in wrapped form and handles authentication, authorization and persistence.

“Zero knowledge” describes the goal that normal web operation requires neither the plaintext password nor decrypted contents or unwrapped master keys on the server. This is not a zero-knowledge proof protocol.

The local admin CLI is an explicit bootstrap exception: it processes the first password and generates the original keys on the machine running the command.

The backend and React frontend implement the client procedures described here. The implementation is tested but has not been independently security-audited.

02 · Keys and responsibilities

Value Generation and purpose Storage
masterEncryptionKey 32 random bytes; wraps individual file keys. Plaintext only in the trusted client; wrapped inside userKey.
masterAuthKey An independent 32 random bytes; HMAC-SHA-256 for metadata. Plaintext only in the client; separately wrapped inside userKey.
passwordKey Argon2id of the password and individual passwordKeySalt; 32 bytes. Only during local key processing.
fileKey A fresh 32 random bytes for each encryption of a file or text value. Wrapped at the beginning of the encrypted object.
loginHash Base64-encoded Argon2id output used for authentication. Sent to the backend, which stores an additional scrypt hash.
JWT signing keys Separate server-side HMAC keys; never content or metadata keys. ./jwtkeys

All authorized users share the same two master keys. Each user has an individual password, passwordKeySalt, derived passwordKey and wrapped representation called userKey. All random values require a cryptographically secure random number generator.

Backend implemented

03 · Bootstrap and password derivation

The server, configuration CLI and admin CLI entrypoints ensure that ./.salt exists. Initial creation generates 32 random bytes stored as exactly 64 hexadecimal characters. Existing values are reused; invalid or unreadable files cause an error. New files use mode 0600 and are published atomically.

The admin CLI asks for a username (at least 3 characters), display name and masked password. It reads the instance value from ./.salt, assigns a UUID v4 and refuses another bootstrap if any admin already exists.

A(P, S) = Argon2id(password=UTF8(P), salt=S,
                     version=0x13, memory=19456 KiB,
                     timeCost=2, parallelism=1, output=32 bytes)

loginHash       = Base64(A(password, UTF8(instanceSalt + username)))
passwordKeySalt = CSPRNG(32 bytes)
passwordKey     = A(password, passwordKeySalt)

0x13 identifies Argon2 version 1.3 (decimal 19). Memory use is 19 MiB. This is the OWASP minimum Argon2id profile. Passwords and string salts use UTF-8 without automatic Unicode normalization. The login salt uses the stored hexadecimal text, not its decoded 32-byte value.

The CLI independently generates the original master keys, wraps them and creates the first user with only the admin role. Temporary plaintext key buffers are overwritten in a finally block; this does not guarantee erasure of every copy of a JavaScript string.

Application configuration and the DynamoDB namespace

npm run config:init asks for the application title first, followed by database and storage settings. Its saveConfig function stores the title in ./conf/app.json, for example { "title": "Meine Videos" }. Existing titles are prefilled; overwriting existing configurations requires confirmation. Titles must contain 1 to 100 characters after trimming surrounding whitespace. Missing app.json defaults to VideoVault; malformed or unreadable existing files cause an error.

When conf.tablePrefix is absent from ./conf/db.json, the DynamoDB adapter derives its prefix from the current title on initialization. Camel-case word boundaries and other separators become hyphens, diacritics are removed and ASCII letters lowercased: VideoVault → video-vault-, Meine Videos → meine-videos-. Titles without ASCII letters or digits use app-<16 hexadecimal characters from SHA-256 of the title>-. Unusually long normalized titles are truncated to 100 characters and also receive a hash suffix. Table names append users, usernames, videos, comments or login-attempts. An explicitly saved conf.tablePrefix takes precedence. The configuration CLI asks for the prefix separately, prefilling an existing value or otherwise deriving its initial value from the title. The confirmed value is saved in the database configuration and remains independent of subsequent title changes.

Configuration changes require a restart. Changing the prefix selects different DynamoDB tables and may create them during initialization; existing data is not automatically migrated. Without an explicit tablePrefix, a title change can also change the prefix. With tablePrefix set, title changes preserve the table namespace. Different titles with the same normalized form can produce the same prefix. The application title does not affect the instance salt, password derivation or master keys.

The title is public display information. Bootstrap exposes only approved application fields, never database or storage credentials. The frontend sets the title as text, for example via document.title, rather than interpreting it as HTML. The app object can later accommodate a logo and favicon; configurable logo/favicon fields are not implemented yet; the frontend uses bundled assets.

Public bootstrap for the client

Before logging in, the client requests GET /bootstrap over HTTPS from the same origin. This route requires no token and returns the protocol version, the public, stable instance salt from ./.salt and the application title under app.title, plus frontend metadata configuration under meta. An example using a fictitious salt value: 

{ "version": 1, "instanceSalt": "abababababababababababababababababababababababababababababababab", "app": { "title": "VideoVault" }, "meta": { "recorded": { "withTime": false, "useAsFilter": true }, "fields": [], "sorting": [{ "source": "recorded", "direction": "desc" }, { "source": "title", "direction": "asc" }] } }

The response schema fixes the version to 1 and requires exactly 64 hexadecimal characters for the instance salt. The client validates the supported version and salt format before deriving loginHash. It uses the exact hexadecimal text received, without changing case or encoding. The instance salt is public and is not a login secret.

The server loads the instance salt and application configuration once before starting the HTTP server. Requests to /bootstrap use this in-memory value without reading files or generating new salts. Cache-Control: no-store prevents persistent HTTP caching; the frontend explicitly stores bootstrap in localStorage and reloads it only when absent or through “Reload display settings”. Swagger documents this route as public.

The instance salt is not rotated on restart and must be backed up with the database. Existing installations must retain the previous salt file's exact contents under its new name ./.salt. Generating a replacement changes login derivation for existing accounts.

Public frontend metadata configuration

npm run meta:init saves ./conf/meta.json. Bootstrap exposes this configuration under meta: recorded presentation/filter options, field keys and display names, types and multiple-value flags, required/details/filter flags, and the ordered sort fields with their directions. These are public field definitions, not video metadata values. Do not put confidential information in field keys or display names.

These settings control the frontend only. Required and visibility flags are neither server-side validation nor access control; hiding a field does not remove it from API responses. Video.meta remains an arbitrary JSON object. Authentication and role checks continue to govern API access. The frontend must render names as text and locally decrypt titles before sorting by their contents. Multiple values are free arrays compared lexicographically, element by element in stored order. Missing values and empty arrays sort last regardless of direction.

The server loads metadata configuration at startup and keeps it in memory for requests. Missing files default to recorded without time, enabled as a filter, no metadata fields, and sorting by recorded descending followed by title ascending. Existing configurations are checked for unique keys, supported types and consistent sort references before publication. Changes require a restart.

04 · Packing and unpacking userKey

wrappedMasterEncryptionKey = AES-256-KW(passwordKey, masterEncryptionKey)
wrappedMasterAuthKey       = AES-256-KW(passwordKey, masterAuthKey)
userKey = Base64(wrappedMasterEncryptionKey || wrappedMasterAuthKey)

Wrapping uses AES Key Wrap from RFC 3394 without padding, with the defined initial value A6A6A6A6A6A6A6A6. Wrapping a 32-byte key produces 40 bytes. Each key is wrapped independently; only the resulting buffers are concatenated. 

bytes = Base64Decode(userKey)        // exactly 80 bytes
wrappedEncryption = bytes.subarray(0, 40)
wrappedAuth       = bytes.subarray(40, 80)
masterEncryptionKey = AES-256-KW-Unwrap(passwordKey, wrappedEncryption)
masterAuthKey       = AES-256-KW-Unwrap(passwordKey, wrappedAuth)

Use Buffer.subarray() or Uint8Array.subarray() to split the data; Node Buffers have no splice() method. Base64 uses the standard alphabet and padding from RFC 4648. Check the decoded length and the results of both unwrap operations before using the keys. Any failure aborts unlocking.

Backend implemented

05 · Authentication and server access

  1. The client obtains the public instance salt from GET /bootstrap and validates the protocol version and format.
  2. The client locally derives loginHash using Argon2id as described above and sends the username and Base64 string over TLS.
  3. The backend treats this Base64 string as the password without decoding it. The database stores a scrypt string with a separate 16-byte salt: N=2¹⁵, r=8, p=3, output 32 bytes. Verification uses timingSafeEqual.
  4. On success, an HS256 JWT is signed with a randomly selected key from ten server-side 32-byte signing keys. Default lifetime is one hour. Verification checks algorithm, signature, key ID, issuer, audience and expiration.
  5. Each authenticated request loads the current user from the database. Roles come from the current account flags, not token claims. API user responses omit loginHash.

The fifth failed attempt for a username starts a 15-second lock. Subsequent failures after expiry double the duration up to 15 minutes. Attempts during a lock restart its duration without increasing the counter. A successful login removes the counter. Concurrent attempts for one username are serialized within the single AuthService instance.

The transmitted loginHash is a reusable login secret. Possessing it enables login without knowing the original password. Never log it, tokens or passwords. TLS remains necessary.

Admins manage accounts, editors manage videos, and moderators can modify other users’ comments. Any authenticated user may retrieve content and manage their own comments. These API permissions are separate from possession of the shared cryptographic keys.

06 · Adding users and changing passwords

Adding another user

The current authorized user locally unlocks their userKey. The new user’s password is used to derive a new loginHash, a fresh 32-byte passwordKeySalt and a new passwordKey. The existing master keys are individually wrapped with that new passwordKey and saved as the new userKey. No new pair of master keys is generated.

In this procedure the provisioning client temporarily processes the new user’s initial password. The frontend provides an invitation link containing a temporary password in its URL fragment; a public-key handover protocol is outside this architecture. The backend receives the completed password attributes; it does not unwrap or rewrap the keys.

Changing a password

The client unwraps the existing master keys with the previous passwordKey. It derives a new passwordKey from the new password and a fresh passwordKeySalt, then rewraps both master keys and computes the new loginHash. The backend hashes this with scrypt and updates loginHash, passwordKeySalt and userKey together.

The master keys and existing content encryption remain the same. A forgotten password cannot unlock the old userKey without already unlocked keys or assistance from another key holder. Password changes currently do not revoke previously issued JWTs.

Changing a username

The username participates in the login salt. The client must therefore derive a new Base64 loginHash from the password and instanceSalt + newUsername. Renaming the user on the backend alone cannot reconstruct this value from the previous hash.

Both backend routes now require a JSON body containing { "loginHash": "…" }: PATCH /api/user/change/username/:username for the current account and PATCH /api/user/change/username/:userId/:username for admins. The service hashes the new loginHash with scrypt and a fresh salt. All five database adapters atomically store the username and scrypt hash together; a name conflict leaves both unchanged. Supplying the same username still updates the supplied hash.

passwordKeySalt, userKey and the master keys need not change, because passwordKey derivation does not depend on the username. An admin also needs the correctly rederived loginHash; the backend receives no plaintext password for this operation. The frontend implements derivation. Administrative renaming also generates a temporary password and rewraps userKey; the two backend calls are not one transaction.

07 · Files: encryption and binary format

For each new encryption of a video or thumbnail file, the client generates a fresh, random 32-byte fileKey and wraps it with masterEncryptionKey using AES-256-KW. Replacing a file also requires a fresh fileKey.

Plaintext is split into chunks of at most 34 KiB = 34,816 bytes. Each chunk uses AES-256-GCM with the same fileKey but its own 12-byte IV. An IV must never be reused with the same fileKey. Generate IVs with a cryptographically secure random number generator and prevent repetitions within the file. Each chunk has a 16-byte GCM tag. 

wrappedFileKey = AES-256-KW(masterEncryptionKey, fileKey)
chunk[i]       = IV[i] || encryptedChunkContent[i] || GCMtag[i]
encryptedFile  = wrappedFileKey || chunk[0] || … || chunk[N−1]

Additional authenticated data (AAD)

AAD is UTF-8-encoded canonical JSON according to RFC 8785, containing exactly these fields:

Field Meaning
version The number 1, identifying this protocol profile.
context video, thumbnail, title, description or comment.
identity For files, the exact storage name <videoId>.video or <videoId>.thumbnail; for text, the video or comment ID.
chunkIndex The integer position of this chunk, starting at 0.
chunkCount Total number of chunks, at least 1. 
{"chunkCount":2,"chunkIndex":0,"context":"video","identity":"<videoId>.video","version":1}

The total plaintext length is explicitly not an AAD field. Use identities unchanged, without Unicode normalization or reinterpretation as local paths. AAD is authenticated, not encrypted, and is not separately stored in the binary container. The client reconstructs it from the known object context and chunk structure. Version 1 uses the sizes defined here; a future version requires explicit protocol agreement.

Boundaries, completeness and range access

Every chunk except the last contains exactly 34,816 plaintext bytes. The last contains 1 to 34,816 bytes; an empty file alone uses exactly one authenticated empty chunk. An encrypted empty file therefore occupies 68 bytes. A full chunk occupies 34,844 bytes. 

C = 34816                      // maximum plaintext bytes per chunk
B = C + 12 + 16 = 34844         // full encrypted chunk size
L = plaintext length in bytes
N = max(1, ceil(L / C))
F = 40 + L + 28 × N             // total encrypted file size
offset(i) = 40 + i × B

For a complete file, chunk count can be calculated as N = ceil((F − 40) / B). The parser enforces a minimum total size of 68 bytes, valid chunk boundaries and permitted sizes, including the empty special case. A partial response must not be interpreted as a complete file; range requests also require the encrypted object’s total size.

The client verifies each GCM tag against the expected AAD before releasing that chunk’s plaintext. Reordering violates the bound index; truncating or appending complete chunks changes the authenticated chunk count; changes within a chunk invalidate its tag. A verified individual chunk does not prove that the remaining download has arrived completely.

A GCM tag is not a separate HMAC-SHA-256 output. It belongs to authenticated AES-GCM encryption and protects ciphertext and AAD. The metadata HMAC has a separate purpose and key.

08 · Video titles, descriptions and comment contents

Video titles, descriptions and comment contents use the same procedure as files: UTF-8 plaintext, a fresh random 32-byte fileKey, AES-KW with masterEncryptionKey, 34-KiB chunks and AES-256-GCM. The complete binary container is then Base64-encoded and stored in the database text field. 

title       = Base64(wrappedFileKey || chunks)  // context="title", identity=videoId
description = Base64(wrappedFileKey || chunks)  // context="description", identity=videoId
content     = Base64(wrappedFileKey || chunks)  // context="comment", identity=commentId

AAD also includes the version, chunk index and chunk count, as for files. A description also uses the video ID as its identity; the separate description context prevents substitution with the title of the same video. Each text value receives its own fresh fileKey. The separate context prevents substitution between a title and a comment with the same ID. Every new encryption, including editing a text value, receives a fresh fileKey. Before display, decode Base64, unwrap the fileKey and verify all GCM tags.

A regularly encrypted empty string is a Base64 container containing an authenticated empty chunk. It differs from content='' on a server-side tombstone. Base64 is only a transport and storage encoding; AES-GCM provides confidentiality.

Backend contract for descriptions and recording dates

New videos require description as an encrypted Base64 string and recorded as the recording timestamp. The server treats descriptions as opaque text of 1 to 1,000,000 characters; client-side encryption follows the title procedure. Empty plaintext is transmitted as a valid encrypted container, not an empty string. The recording timestamp is visible, represented as a Date in the domain model and serialized to HTTP JSON as a UTC ISO timestamp. Its complete normalized value enters the metadata HMAC, while descriptions contribute only their stored length.

The editor routes PATCH /api/video/change/description/:videoId and PATCH /api/video/change/recorded/:videoId require the corresponding new field plus lastModified and hmac. VideoService and all five database adapters support these updates; the corresponding field, lastModified and HMAC are stored together atomically. Other fields are preserved. The backend does not generate or verify description encryption or metadata HMACs itself.

09 · Metadata integrity and tombstones

The client generates the metadata HMAC with masterAuthKey and HMAC-SHA-256. Its input is a canonical representation of all business attributes of the video or comment record, following these rules:

  1. Exclude the hmac field and internal database helper fields.
  2. Replace encrypted text values with their length as stored: title, description or content becomes a number instead of the Base64 string in the HMAC projection. For canonical Base64, the character count equals the UTF-8 byte count and includes padding. It is neither plaintext length nor decoded container length.
  3. Preserve all other attributes, including IDs, MIME types, JSON meta, the unencrypted recording timestamp recorded, timestamps, and, for comments, author, video association and flags.
  4. Represent dates as UTC ISO strings equivalent to toISOString() before canonicalization. The projection must contain valid JSON values only, with no undefined or non-finite numbers.
  5. Serialize using RFC 8785 (JCS), encode as UTF-8 and apply HMAC-SHA-256. Store the 32-byte output as standard Base64.
projection(video)   = allBusinessAttributesExceptHmac(video)
projection.title       = storedVideo.title.length
projection.description = storedVideo.description.length

projection(comment) = allBusinessAttributesExceptHmac(comment)
projection.content  = storedComment.content.length

hmac = Base64(HMAC-SHA-256(masterAuthKey, UTF8(JCS(projection))))

Keep field names unchanged: for example, replace "title":"…" with "title":92 in the projection rather than introducing an extra titleLength field. Updates require a new HMAC over the complete resulting record. The client verifies it before use; the backend stores it but cannot verify or generate it without masterAuthKey.

The metadata HMAC deliberately binds only the stored length of encrypted text, not its actual Base64 contents. GCM tags provide content authentication. The metadata HMAC alone therefore cannot identify an earlier valid ciphertext for the same context and identity with the same stored length as stale.

Exception: server-side deletion markers

For soft deletion, the backend sets deleted=true and content=''. This applies to own-comment deletion, moderation and deletion of a user’s comments. Without masterAuthKey, the server cannot produce a new valid HMAC for the modified record; the old HMAC must not be treated as valid evidence.

Tombstones are explicitly not cryptographically verified. The client displays a server-side deletion marker rather than an authenticated comment and does not attempt to decrypt the empty content. Remaining tombstone metadata is not cryptographically confirmed either. A malicious server can consequently hide content by marking it deleted; this architecture does not prevent deletion or suppression of data.

10 · Protection and limitations

Implemented browser and offline behavior

The standalone React project in frontend/ is a PWA over HTTPS (localhost also works for development). The service worker caches local application assets only. JWT, bootstrap and the user profile containing the wrapped userKey are stored in localStorage. The JWT is a bearer secret: same-origin malicious code can read it; XSS or a compromised frontend can also capture unlocked keys and plaintext.

Each reload requires the password for local unlocking. Decrypted master keys remain in the open page’s memory only. A 401 or logout removes the token and active media capabilities. Offline unlocking uses the previously loaded profile and a token that has not expired locally; it is not a current server-side permission check. UI roles never replace backend authorization.

IndexedDB stores the catalog with encrypted titles and descriptions, the latest synchronized modification time and previously loaded encrypted thumbnails, separated by instance salt and user ID. Decrypted texts and thumbnails are not stored there. Business metadata, including recorded, remains unencrypted as on the server. “Clear offline data” removes this account’s cache; ordinary logout retains the encrypted cache.

Synchronization first requests /api/video/0, then changes since the highest known lastModified. /api/video/catalog provides authenticated users with current IDs to remove deleted entries. Ciphertext and cursor are persisted together only after successful integrity checks. Reconciliation is not cryptographic proof against suppression, a transactional snapshot, or protection against incorrect client clocks or backdated changes.

Range playback and download

The backend supports authenticated HEAD and HTTP Range requests for encrypted video bytes. A temporary random service-worker media path turns player requests into messages to the unlocked page. The page fetches complete affected chunks, checks tags and AAD, and returns only the requested plaintext bytes. The service worker streams those bytes in bounded blocks to the player or download; plaintext videos are never persistently cached. The page must remain open and unlocked. Videos are initially online-only.

Password rules and invitations

The frontend requires at least 12 characters and three of four categories (uppercase, lowercase, numbers, special characters). This UI rule does not replace an additional server-side policy. On submission, the browser queries the Pwned Passwords range API: only five hexadecimal SHA-1 characters are sent, with Add-Padding: true; the full comparison stays local. SHA-1 is used for lookup only, never password derivation. The service sees the IP address and prefix. Breached passwords are rejected; outages allow continuation with a warning.

For creation or an administrative password reset, the browser generates a random temporary password and rewraps the shared master keys. A link displayed once contains {type: invite|reset, username, password} as Base64url JSON in its fragment. Fragments are not sent in HTTP requests but remain secrets: history, clipboard, extensions and recipients can read them. The app immediately scrubs the fragment upon reading and then requires a password change. This requirement is explicitly enforced in the frontend only; links have neither server-enforced single use nor a separate expiry time. Password changes do not revoke existing JWTs.

The architecture protects content confidentiality from a server or storage system that handles encrypted data only. Authenticated encryption detects tampering within its bound context, and the shared HMAC protects metadata integrity against parties without masterAuthKey.

Boundary Meaning
Visible metadata Usernames, display names, roles, IDs, relationships, timestamps including recorded, MIME types, file sizes and access patterns remain visible to the backend. meta is not automatically encrypted; plaintext values placed there remain readable.
Shared keys Deleting an account blocks further API access but does not revoke keys or data already copied. Cryptographic revocation requires key rotation and potentially re-encryption; it cannot make previous copies unreadable.
No individual signature Every masterAuthKey holder can generate valid HMACs. A valid HMAC therefore cannot prove which individual user created a record; the backend enforces roles and author assignment.
No automatic freshness An earlier valid record or file can be replayed. Including timestamps in an HMAC binds their values but does not prove freshness without trusted comparison state.
Client trust XSS, compromised browser extensions or modified delivered JavaScript can steal passwords and keys. Confidentiality assumes trusted client code and a trusted endpoint.
Password attacks A stolen userKey and passwordKeySalt enable offline password guesses using unwrap verification. Argon2id increases their cost; strong passwords remain necessary.
Recovery Without an available authorized key holder, the server cannot recover the master keys. Backups must consistently preserve the database, storage, stable instance salt and required configuration.

“Zero knowledge” is therefore a bounded architectural claim, not a promise that an active server attacker, authorized key holder or compromised client cannot cause harm.
